요청 원문: "코드품질, 테스트우선, 접근성, 성능원칙을 정의해줘."

[I. 코드 품질]
- 클라이언트 코드는 npm run lint 를 통과하고, 병합 전에 Prettier 형식을 따라야 한다(MUST).
- 백엔드 Python 공개 함수는 모두 타입 주석을 달아야 하며, 요청·응답 본문은 Pydantic 모델을 써야 한다(MUST).
- routes/ 의 핸들러는 SQL이나 DB 드라이버를 직접 호출하지 않고, persistence/ 를 거쳐야 한다(MUST).
- 주석 처리된 코드, 쓰지 않는 import, 죽은 코드는 병합하지 않는다(MUST).
- 실행 시 쓰는 모든 패키지는 requirements.txt 또는 package.json 에 명시한다.
  간접 의존성에 기대는 것은 허용하지 않는다(MUST).

[II. 테스트 우선 (필수)]
- 바뀌는 API 엔드포인트와 영속성 연산마다, 구현 전에 실패하는 pytest 테스트를 먼저 쓴다(MUST).
- 백엔드 버그 수정에는 실패 후 통과하는 회귀 테스트를 추가한다(MUST).
- 클라이언트 버그 수정은 quickstart.md 의 수동 검증으로 확인하고, 병합 요청서에 실행한 검증 항목을 적는다(MUST).
  클라이언트 테스트 프레임워크는 별도 기능으로 도입할 수 있다(MAY).
- Docker 'test' 스테이지가 통과해야 'final' 이미지를 빌드한다(MUST).
- 테스트는 실제 MySQL 서버를 요구하지 않고, 상태를 공유하지 않는다.
  SQLite 테스트는 테스트마다 임시 DB 경로를 써야 한다(MUST).

[III. 접근성]
- 모든 대화형 컨트롤(완료 토글, 삭제, 추가 폼)은 키보드만으로 조작할 수 있고, 보이는 포커스 표시가 있어야 한다(MUST).
- ItemDisplay.jsx 의 아이콘 버튼은 동작과 항목 이름을 담은 접근 가능한 이름을 가져야 한다(MUST).
- 추가 입력창은 레이블과 연결되고, 비활성 상태가 보조 기술에 전달되어야 한다(MUST).
- 완료 상태는 색만으로 나타내지 않는다. 아이콘이나 글자를 함께 쓴다(MUST).
- 텍스트와 대화형 컨트롤은 WCAG 2.1 AA 명암 대비(일반 텍스트 4.5:1)를 만족해야 한다(MUST).
- 빈 목록 문구는 글자로 표시한다(MUST).
- 추가·삭제·토글은 aria-live 영역으로 알리는 것이 바람직하다(SHOULD).

[IV. 성능]
- 모든 DB 입출력은 비동기로 한다(aiosqlite / aiomysql). 요청 처리 중 블로킹 호출은 금지한다(MUST).
- MySQL 커넥션 풀 범위(최소 1, 최대 5)는 부하 측정 결과를 근거로 한 경우에만 바꾼다(MUST).
- 각 CRUD 엔드포인트는 지연 시간 예산을 지켜야 한다. 예산은 SQLite에서 측정한 뒤 정한다(MUST).
  현재 예산은 미정(TODO(PERF_BUDGET))이다.
- 프로덕션 산출물은 npm run build(Vite)로 만들고, 개발 전용 패키지는 final 이미지에 넣지 않는다(MUST).
- 클라이언트는 한 번의 변경 뒤 전체 목록을 다시 받지 않고, 변경 응답으로 목록을 갱신하는 것이 바람직하다(SHOULD).

[추가 제약]
- 기술 스택은 requirement-KR.txt §7 에 고정한다(Python 3.12, FastAPI, Pydantic v2, aiosqlite/aiomysql,
  Node.js 22, React 19, Vite 6, React-Bootstrap). 메이저 버전 변경은 헌법 MINOR 개정이 필요하다.
- SQLite와 MySQL 모두 재시작 후에도 데이터가 유지되어야 한다(MUST).
- CORS 전체 허용(NFR-02)은 개발용이다. 배포 전에 운영 출처 목록을 정해야 한다(TODO(CORS_PROD)).
- Windows MIME 타입 강제 등록(NFR-03)은 유지한다(MUST).
- compose.yaml 의 자격 증명은 개발용이다. 운영에서는 Docker secret 또는 환경변수를 쓴다(MUST).
- 생성물 폴더(backend/.venv, .pytest_cache, client/dist, backend/src/static)는 커밋하지 않는다(MUST).

[개발 워크플로]
- 기능 작업은 Spec Kit 순서를 따른다: specify → clarify → plan → tasks → implement.
- 병합 전에 다음이 모두 통과해야 한다(MUST): backend 의 pytest, client 의 npm run lint 와 npm run build,
  Docker 'test' 스테이지.
- 코드 리뷰는 위의 원칙을 모두 확인한다. 위반은 고치거나, 병합 요청서에 정당화를 적고 리뷰어가 승인해야 한다(MUST).

[거버넌스]
- 이 헌법은 저장소의 다른 개발 관행보다 우선한다.
- 개정은 헌법 파일을 고치는 병합 요청으로 하며, 동기화 영향 보고서를 포함하고 관리자 승인을 받아야 한다(MUST).
- 버전 규칙(의미 체계 버전):
  - MAJOR: 원칙을 제거하거나 의미를 뒤집는 개정
  - MINOR: 원칙이나 섹션을 추가하거나 지침을 크게 확장하는 개정
  - PATCH: 의미가 바뀌지 않는 문구·오타·명확화
- 2.0.0 개정 이유: II의 회귀 테스트 요구를 백엔드 버그로 좁혔다(의미 변경 → MAJOR).
